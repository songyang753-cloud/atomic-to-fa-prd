# PRD交互设计生成规则

本文件是生成时的决策依据。基础来自 Owl-Listener conversational-ux 的轮次、确认、修复、语音表达及人格方法；以下决策优先级和耳机场景流程为本项目扩展。用于产品需求已确定后产出PRD交互章节，业务对象、费用、服务边界、权限和成功条件以需求为准。

## 一、把需求变成可设计的任务

从需求直接提取每个用户目标及其业务对象。一个目标可以跨多轮；查询与执行可处于同一流程。为每个目标整理：入口、必要信息、可用上下文、业务动作、结果凭据、持续时间、用户控制、能力依赖。不要要求用户重新填写已经提供的信息。

区分三类空缺：
- 业务决定：目标对象、收费或成功标准不明会改变流程时，问最关键的一项；独立部分继续生成，相关分支标“待业务决定”，不虚构。
- 交互决定：追问顺序、候选表达、反馈层次等按本文件直接决策，写出结果和理由，不留给用户设计。
- 能力未知：默认在已确认范围内给可行退路，缺口单列附录；只有显式 target-experience 模式才展开目标流程。采集接口、等待参数、取消能力等不写成已上线事实。

不把每个业务包装成新Agent。产品已定义FA时沿用；需要多FA时明确各自负责的业务，不新造OS分工。

## 二、按顺序作出交互决定

下表从上到下决策；前置问题解决后重新计算后续流程。具体节点只应用实际相关规则。

| 判断 | 采用的交互 | 必须生成的分支 |
|---|---|---|
| 任务对象或用户目标有多个合理解释 | 澄清目标，先不给业务承诺 | 候选、都不是、用户改口 |
| 缺少权限或能力 | 进入已有权限/能力流程 | 同意、拒绝、失败、恢复；FA缺权按现有失败与用户重试机制 |
| 必要信息缺失 | 信息补全 | 一次答全、部分回答、不知道、纠正、无响应 |
| 同一信息多个候选 | 候选消歧 | 选择、按特征选择、下一批、都不是 |
| 信息足够且仅查询 | 查询并回答，通常无需单独确认 | 无结果、结果过期、服务失败、用户追问 |
| 改变可恢复的个人记录且请求明确 | 以请求作为执行授权，结果中复述关键内容；业务另有确认要求时从其规定 | 保存成功、失败、纠正、重复请求 |
| 付费、对外发送、不可恢复或错误后果高 | 执行前显式确认 | 同意、拒绝、修改、含糊回答、无响应 |
| 用户已明确授权精确动作和关键条件 | 复用仍有效的授权，避免重复确认；实际条件改变时重新确认 | 报价或对象变化、授权失效 |
| 立即无法得到结果 | 等待或后台执行 | 用户问进度、停止播报、取消任务、超时、迟到结果 |
| 长时引导/内容/监测 | 启动说明后分段或事件式交互 | 暂停、继续、跳过或调整、结束、失联 |

冲突时优先满足明确业务确认要求、权限条件和高后果动作规则；“用户说了帮我办”不足以授权后来新增的费用、收件人或交易条件。

## 三、标准流程配方

生成时用业务内容替换配方变量，展开实际分支；不得把配方原样留在PRD中。

### 配方A：收集与消歧

1. 从本轮请求提取全部已给信息，再使用获准且有效的上下文。标明上下文来源；无法确定指代时先澄清对象。
2. 只收集完成任务所需信息。追问优先级：决定任务能否执行的条件→影响其他参数的条件→当前最易回答的剩余项。相同条件下按自然业务顺序，不按接口字段顺序。
3. 每轮问一个决策问题；用户主动补充多个信息则全部接收。已有有效值不重复询问。
4. 候选有可读区分特征时读“名字＋最少区分特征”；默认一批不超过三个，允许说名字、序号或特征选择。更多时支持下一批；更新候选后旧序号失效，必要时复述新选择。
5. “都不是”时问一个能缩小范围的条件；“不知道”时提供真实可得的辅助信息或可选默认值。只有业务已允许的可选项可以跳过。
6. 局部纠正只替换相应信息。重算关联项：改目的地可能影响路线、费用和确认；改提醒内容通常保留时间。PRD必须列本业务的依赖关系。
7. 无响应与无法识别按配方C处理；信息充分后进入查询或确认/执行。

### 配方B：确认与提交

显式确认时读出“要做的动作＋准确对象＋影响决定的条件”，以单一明确问题结束。省略不影响决定的内部字段。执行授权只对当前任务、对象及对应条件有效。

| 回答 | 下一步 |
|---|---|
| 对当前问题明确的“是/确认/好/就这样” | 条件未变化且权限齐备时提交一次 |
| “不/算了” | 不提交；明确取消当前提议，保留或清除草稿按业务规则 |
| “改成……” | 更新对应值，重新计算依赖，再生成必要确认 |
| “随便/你看着办” | 有业务预授权范围时按范围选择并说明；否则问清关键条件，不推定付费或对外授权 |
| 同时提出新任务 | 处理新目标并保留原任务未确认状态；原“好”归属不明时核对 |
| 沉默或识别失败 | 保持未确认，按配方C处理 |

确认有效性还取决于用户已实际听到动作、对象和关键条件；在关键条件播完前插入的“好”先停止旧播报并补齐未听到条件，再取得明确答复。已在本次有效上下文中完整告知的条件可复用，不强制机械重播。提交前再次核对报价、对象和授权有效性；排队、断连或等待期间失效则重新查询并确认。

提交后按完成凭据播报结果。“收到请求”对应正在处理；创建记录、订单确认等业务凭据对应完成。结果未知时保留原操作；有可定位原操作的标识才查询，无标识时说明核实受阻并等待可用凭据，不承诺必然查回，不启动重复提交。重试和换服务按用户选择与服务支持处理。

### 配方C：修复与退出

生成时分别处理：没有发言、发言但识别失败、理解部分、输入不匹配、超范围、业务失败。避免将这些情况合并成“请再说一次”。

默认修复策略：第一次给更短、更定向的问题；第二次换成例子、拆分或候选；继续失败则提供实际支持的替代方式或结束本次收集。此为本产品初始设计默认，PRD可因持续陪伴、无障碍等场景调整并解释。用户任何时候明确退出均立即处理，无需耗尽次数。

同一待解决问题连续失败才递进；成功得到所需信息后重新计数。等待上限从实际问话完成、可接收答复时开始，具体值优先沿用平台配置；未知写明待验证参数及用户观察到的行为。不能从输出队列入队时开始算用户无响应。

退出时只说明当前任务状态、需要用户做的下一步和实际可用恢复方式。草稿保留内容、有效期和恢复标识需有依据；未支持恢复则明确重新发起所需信息，不承诺“下次自动继续”。

### 配方D：打断、变更与取消

用户发言时先确定是在回答、附和、纠正、控制还是新目标，短促的“停”“不”也要保留有效性。语境不足则问一个最小澄清问题。停止旧输出后仅在原内容仍适用时恢复。

| 当前业务状态 | 修改条件 | 请求取消 |
|---|---|---|
| 未提交 | 更新信息及依赖，按需重确认 | 结束提议或草稿，说明未执行 |
| 已提交、处理中 | 保留原操作，先确定是否支持变更 | 发起服务支持的取消并查询结果；反馈取消中 |
| 结果未知 | 保存新意图，先核对原操作 | 核对原操作及取消状态，说明仍在核对 |
| 已完成 | 按支持的修改流程创建后续关联任务 | 查询是否支持撤销/取消及费用，必要时再次确认 |

“别说了”默认控制播报；有“取消订单/结束导航”等对象时控制业务。“停”在导航、内容等持续任务中按当前活动语境处理；存在多个可指对象时先停播，再问要结束哪个业务。PRD写出本业务的默认解释。

### 配方E：等待、异步和多任务

能快速完成则直接反馈；达到平台等待反馈条件时，说明实际阶段和用户是否需要等待，不编造百分比。长时任务仅在支持后台时告知“可以先做别的”。

进度发生有意义变化、需要用户决定、完成或失败时反馈；避免循环占用耳机。结果返回时加最短任务锚点，例如“刚才那笔叫车……”。旧请求已被修改时，旧候选和报价不再用于当前决定；已发出交易的迟到结果须记录到原操作，处理真实订单及取消意图，不能统一丢弃旧结果。

并发采用已有IO调度：明确结果是否紧急、是否需要答复、有效期及能否延后。新任务不能把其他任务的“是”拿来授权。用户正在通话、摘下或断连时，按支持能力延后或停止呈现；恢复时核对结果新鲜度和业务状态，不重播整段历史。

### 配方F：拍照、定位和持续服务

拍照：确认需识别的目标→权限与可用性→指引用户对准目标→实际采集反馈→质量判断→识别/重拍→结果和后续。用户已明确要求拍照且授权有效时不额外问“要拍照吗”。失败时定向说明遮挡、光线等可证实问题；无法判断原因则说明未获取可用画面。重拍不会重复执行业务副作用。

定位：区分当前地点、用户指定地点和历史地点；按业务要求检查精度和时效。位置不足时让用户口述或选择地点；导航等需要实时位置的业务在条件不足时停止提供伪实时引导，说明恢复条件。硬件存在不能直接确定连续定位可用。

持续服务：明确一次启动后的服务范围、反馈触发、暂停/结束、后台条件及失效方式。导航按路线事件反馈、内容按段落反馈、监测按有效事件反馈；不要把每个片段重新做成问答。旁插查询后按仍有效的位置继续，不重复启动。

### 配方G：开放式对话与互动内容

区分系统叙述、等待用户决策和暂停三种阶段。自由表达按目标理解，不把用户限制为固定口令；用户行动在内容规则内则推进，有冲突则说明限制并给一个可行方向。附和只表示听到，不自动代替用户做影响剧情的选择。

叙述中的“继续”接续内容，决策点的“继续”只有在用户已授权代选时才代选，否则问清行动。决策点沉默先定向帮助，仍无回答则暂停，不替用户选择。重说只复述当前内容，不重复结算行动或推进剧情。

暂停保留哪些内容、可恢复多久以及能否跨会话必须明确。恢复从实际支持的语义边界接续；未播部分和已播部分分别处理，状态丢失时说明并让用户决定重启。结束与暂停的保存行为分开写。旁插任务后回到仍有效的上下文，必要时询问是否继续。以上按业务相关性应用，不把交易确认规则强加给每个普通内容轮次。

## 四、输出话术的生成规则

结果或当前状态先说，再给必要解释和一个下一步。面向耳朵写短句。候选分批、长答案先概述并支持展开；内容播放和陪伴可按目标连续输出。不要把所有业务限制为八秒内；八秒来自基础Skill的短反馈建议，最终由内容类型和试听决定。

每条话术注明当前可以回答什么或可以做什么，避免无对象的“确认吗”。时间、地点、金额、联系人等使用足够区分的读法；价格区分预估与最终。状态音、手机承接或人工支持只有确认可用时才写入用户路径。

保持主入口身份和语气一致。业务服务身份影响费用、权限、责任或用户选择时说明。语音人格不替代真实业务状态。

## 五、生成完成后逐步走查

按正常输入走一遍，再对每个有用户输入的节点分别放入：部分回答、纠正、否定、不知道、无响应、退出。对每个外部动作放入：拒绝、失败、超时未知、执行中取消。适用时加拍照/定位失败、异步迟到、任务切换、摘下/断连。输出应能确定下一步和任务最终状态；发现空分支先补设计再交付。

检查是文本设计走查，不宣称运行通过。实际音频、设备和业务验证分别列状态。

## 六、交付成熟度

生成后给出当前阶段：可评审交互稿、可供研发实现、或已完成真实验证。可评审稿允许明确标注能力缺口；交研发前，所有影响分支的业务决定、超时/重试/恢复参数、服务状态及取消能力须有确定取值或确定契约。平台没有既定参数时，提出本场景的初始建议值、理由和验证方法，标为设计建议，不能冒充实测性能；服务契约无法推定时列为阻塞项。每项缺口写清影响节点、需要谁作何决定及如何验收，不能仅写“待确认”。

文本走查覆盖完整可交评审；真实音频的可听清、插话时机和设备事件仍需音频/设备测试；实际成功及取消需业务服务验证。交付物的成熟度取决于未解决事项，不由文档篇幅或用例数量决定。
