# 基于 conversational-ux 的耳机交互设计规则 V0.1

## 基础与适用方式

本规范以 [Owl-Listener / conversational-ux](https://github.com/Owl-Listener/designer-skills/blob/main/interaction-design/skills/conversational-ux/SKILL.md) 为基础，在其对话轮次、确认策略、错误恢复、语音表达、多模态和人格原则上增加耳机产品要求。2026-10-28读取上游正文。下文为本项目的适配与细化，非上游原文转载。其他语音资料只作补充。

用于任何业务子Agent PRD：先识别交互机制，再按本文作出具体决定；不能用“遵守通用规范”替代业务条件、实际话术和异常去向。PA/MA/FA职责沿用现有子Agent规范及其架构依据，不在本次另建架构。

## 1. 对话轮次：让用户知道现在需要做什么

每轮先明确用户目标、已知信息、当前缺口、执行状态和下一步。系统默认一次只提出一个需要作答的问题；用户一次提供多个有效信息时全部接收。直接请求已完整时进入相应流程，无需先问“需要什么帮助”。

| 当前情况 | 处理规则 | PRD必须写明 |
|---|---|---|
| 信息完整 | 校验后查询或进入适用确认，不重复收集 | 充分条件、下一步 |
| 缺少必要信息 | 只问当前最影响继续执行的一项 | 必填依据、顺序及回答示例 |
| 信息有歧义 | 提供可区分候选；候选多时分批 | 区分依据、候选读法和下一批方式 |
| 用户回答超出当前问题 | 接收有效信息，重新计算缺口 | 可同时接收的信息及冲突优先级 |
| 用户要求解释 | 先解释问题用途，再回到原问题 | 保留的信息、恢复位置 |
| 用户表达新目标 | 判断补充、修改或切换；指代不清才追问 | 原任务是否继续、怎样恢复 |

追问在实际呈现且进入可答状态后开始计时；在队列中等待时不算用户未响应。具体等待时长由平台能力与场景共同确定，未知标待验证，不能把静音检测时间直接当作用户思考时限。

## 2. 确认：根据错误后果选择

沿用上游显式、隐式、不确认三类策略，按业务后果细化。具体PRD必须选择并说明依据。

| 条件 | 默认策略 | 示例 |
|---|---|---|
| 低后果查询、结果容易纠正 | 不单独确认，直接回答并带必要上下文 | “杭州今天……” |
| 低后果、容易恢复，仍有后续收集 | 隐式确认，允许随时纠正 | “明天上午。需要提醒你什么？” |
| 金钱、对外发送、难恢复操作或关键歧义 | 显式确认最终对象、动作和关键条件 | “从公司到虹桥站，预估……元，现在叫车吗？” |
| 确认后关键值改变 | 失效原确认，重新校验受影响部分 | 改目的地后更新价格与确认 |
| 沉默、环境声音或其他任务中的“好” | 保持未确认，核对归属 | “你是确认这次叫车吗？” |

确认须绑定当前任务和对应信息版本。用户要求停止播报时先让话；取消订单等业务动作按实际状态处理。不得把“已听到确认话术”假设成事实；未播出部分影响授权内容时需补齐或重新确认。

## 3. 错误恢复：每次重问都增加帮助

沿用上游无输入、无法匹配、超范围、部分理解四类。语音识别缺失但检测到真实发言时，按输入处理失败处理；避免归因为用户没说话。

| 类型 | 首次处理 | 再次失败 | 退出或恢复 |
|---|---|---|---|
| 无输入 | 简短提示当前问题 | 给更容易回答的形式 | 暂存可恢复信息，说明如何继续 |
| 无法匹配 | 指明不确定的部分 | 给例子或可区分选项 | 提供已支持替代或结束本次收集 |
| 部分理解 | 保留已知，只问缺口 | 缩小问题范围 | 不要求整段重说 |
| 超出范围 | 说明当前可做的范围 | 给相关可行入口 | 用户决定继续或退出 |
| 信息冲突 | 指出两个冲突值 | 定向确认最终值 | 暂不执行依赖该值的动作 |
| 服务失败 | 说明失败环节及已保留内容 | 按真实支持能力提供用户可选重试 | 不自动换服务执行业务 |
| 执行结果未知 | 告知正在核对结果 | 查询原操作状态 | 保持原操作身份，明确后续通知方式 |

上游三阶段恢复阶梯用于改变策略：重新表达→示例或约束选项→退出或替代。本项目不统一规定所有业务第三次必退出；PRD填写按字段或步骤计算的重试上限、原因、清零条件和恢复入口。无屏耳机默认不提供不存在的按键、屏幕或人工客服；替代渠道须有能力依据。

## 4. 为耳朵写：短、清楚、能控制

先讲结果或当前状态，再讲用户下一步。一次一个主要结论。问题放在简短说明之后，问完让话。候选默认每批至多三个，超过则分组或继续听下一批；此为设计默认，可根据任务和试听调整。上游“尽可能八秒以内”作为短反馈参考，不约束导航、陪伴或内容播放的全部输出。

PRD逐类规定：人名与地名歧义如何区分；时间是否需日期/星期/上午下午；金额的币种与预估属性；数字逐位或按数值朗读；长内容如何概述、展开、重复和继续。中文规则以实际音色试听确认，不能直接套英文缩写读法。

状态音只在已支持且能被用户理解时使用；说明开始收听、采集或完成分别依靠什么反馈。持续对话中避免每轮重复提示音和“我听到了”。敏感内容明确是否先询问再读、允许概述或延后；耳机佩戴状态不能独自证明适合播报。

## 5. 打断与控制：保留用户最新意图

| 用户输入 | 交流处理 | 业务处理 |
|---|---|---|
| “嗯”“对” | 结合当前问题判断附和或回答 | 只在明确归属的确认环节采纳 |
| “不是，是……” | 让话，收集纠正，不续播旧答案 | 更新关联值，重新校验受影响步骤 |
| “别说了” | 停止旧输出 | 按语境保留业务任务；不清楚时简短澄清 |
| “取消这次叫车” | 让话并承接取消 | 根据未提交、在途、未知、完成状态处理，回报真实结果 |
| “等一下” | 暂停交流 | PRD规定任务是否继续、暂停有效期和恢复方式 |
| 新请求 | 明确承接并处理音频优先级 | 原任务继续、暂停或结束须有规则 |

短促的“停”“不”仍需可被接收。误打断只有在原回答仍适用且能恢复时续播；纠正后抑制旧回答和过时结果。具体停止播放时延、噪声识别和误打断恢复能力均需设备验证。

## 6. 耳机感知与主子Agent扩展

用户从统一入口交流。业务FA提供所需信息、业务状态及交互需求，按已有MA与IO机制承接呈现；不让每个FA自建音频抢占策略。跨FA切换保留必要目标与未决事项，按权限传递，避免用户重复讲述；服务身份影响选择、费用、授权或责任时明确告知。

拍照/GPS类步骤写明为何采集、何时采集、何种反馈、用户怎样配合、质量与时效要求、失败怎样继续。本轮新采失败时说明失败或请求重采；历史材料使用时标明来源和时间。持续采集与一次采集分别说明启动、暂停、停止及结果过期。

多任务由统一交互编排管理声音；每项异步反馈包含足够任务锚点。来电、摘下、断网、重新连接时分别写清输入、播放、采集和业务任务去向。手机等辅助渠道作为已确认可用的补充，PRD明确何时必须转移、用户怎样返回；语音主流程须在无屏条件下表达完整。

## 7. 人格与任务节奏

统一称呼、身份、语气和失败表达；业务差异体现在专业内容与节奏。查询简洁、导航及时、陪伴允许展开，均支持用户调整或结束。被问及身份如实说明；不把拟人化表达当作业务进度或能力凭据。

PRD给出正常、等待、纠错、失败、退出各一组适用话术；避免每个子Agent引入不同的默认人格。特定角色体验须明确角色范围、退出入口和与真实服务身份的关系。

## 8. 每份PRD的完成要求

正文应独立给出用户场景与成功标准、正常完整流程、上述适用机制的具体决定、关键对话及失败后的可行去向。附件记录参数、状态、责任和规则追溯。

每个关键交互节点至少说明：触发条件、已知信息、系统判断、业务动作、用户实际听到的内容、可回答或可控制的方式、无响应/纠正/失败后的去向、预期最终状态。差异填写具体值或决策依据，确实不适用时说明理由。

验收分别检查：文本分支和业务状态；实际音色的清晰度与读法；真实耳机的收听、打断与设备事件；真实服务的完成或取消结果。当前本文为设计规则，以上运行效果尚待验证。

### 样例：改目的地时的处理

用户：“叫车去虹桥站。”系统收集并确认上车点、目的地及实际服务要求的条件。用户在报价播报中说：“不是，去虹桥机场。”系统让话，确定具体航站楼；保留仍有效的上车点。未提交时重新查询并确认；已提交或结果未知时先核对原订单，再提供业务支持的修改或取消方案。费用、订单状态和取消结果按服务返回播报。

对应验收：纠正后不继续旧报价、不重复问已有效的上车点、原订单去向清楚、新目的地关键歧义得到消除、用户确认绑定更新后的条件。此为文本设计示例，真实叫车能力未验证。
