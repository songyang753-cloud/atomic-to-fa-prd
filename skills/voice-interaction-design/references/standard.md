# 语音交互规范 V0.1

状态：初始设计基线，2026-10-28。尚未完成真实设备验证。适用：以语音为主要入口、支持多轮交流及任务执行的产品；具体能力以产品配置为准。

## 目标与使用方式
用户能知道系统是否在听、理解了什么、正在做什么，以及如何纠正和退出。设计功能时先明确业务目标，再选交互模式，引用本规范处理共性行为，最后补充业务例外与验收。

规范中的“必须”用于结果正确性、授权和状态一致性；表达风格与时长是默认策略，可以基于任务、用户偏好和实测调整。用户要求详细解释时允许长答，不套用固定八秒或三个选项的通用上限。

## 一、表达与信息组织
先给用户当前最需要的结果或下一步，额外解释按需展开。用口语，重要数字、时间、对象要能听清。追问围绕当前阻塞点，用户一次提供多个参数时全部接收。列表过长时分组、概述或交给已支持的屏幕；语音仍需提供可独立理解的结论。

## 二、理解、追问与确认
没听到、没听清、意图有歧义、参数缺失和能力不支持分别处理。只补缺失或不确定的内容，保留其余有效信息。连续修复失败时改变提示策略，提供示例、选择或可行退出；次数由产品和场景设定。

确认成本与错误后果匹配。低风险且易恢复的任务可以直接执行或隐式确认；高影响、难撤销或对象有歧义的任务需要明确确认。确认绑定对象与参数，关键参数变化后重新判断确认需求。

## 三、听说轮次与全双工
区分用户思考停顿、说完、附和、要求停播、纠正、取消任务和新请求。基于语义及可用声音信号决定行为，单纯检测到声音不足以确定用户意图。支持打断时，接受有效打断后及时停止过时播放，使用用户实际听到的内容续接。无法确定“停一下”是停播还是取消任务时，先停播，再结合任务风险与状态作简短澄清。

## 四、执行、等待与结果
对外反馈跟随真实任务进度。受理时可说“我查一下”，收到权威成功结果后才能说“已设置”。等待提示应有帮助且真实，避免反复填充“正在处理”。长任务期间的新问题、修改和离开都要有去向。已受理、执行中、成功、明确失败、结果未知分别设计。

## 五、恢复与结束
任务超时且结果未知时先核实状态，再决定重试。迟到结果需结合用户当前意图处理，过时结果不直接覆盖新请求；已发生的业务动作仍要核对并向用户说明。结束前交代未完成任务的去向。用户主动退出时尊重其意图；后台继续、通知和取消以产品支持及用户授权为依据。

## 六、设备与反馈
在产品支持范围内，用提示音、简短语音和屏幕表达收听、等待及完成。先设计每种反馈传达的意义，再选择呈现方式。屏幕可展示长列表和复杂细节；关键结果、下一步和错误仍需有可用语音路径。音频私密性、通知时机及路由遵循产品配置。

## 附件 A：可执行规则
每条含条件、动作、例外、正反例及验证，供生成和评审使用。

| ID | 适用/触发条件 | 必须或默认行为 | 例外/边界 | 正例 / 反例 | 验收 |
|---|---|---|---|---|---|
| E01 | 所有回复 | 默认先结果或下一步，再可选细节 | 教学、故事及用户要求长答可展开 | “明天有两场会，先说上午的……” / 无关开场铺垫 | 首段含当前所需信息 |
| E02 | 数字、专名、日期 | 采用目标音色可读形式，歧义时澄清 | 专业缩写可按受众调整 | “下午三点” / 播读原始时间戳 | 目标音色试听，关键值可理解 |
| U01 | 部分信息已知 | 仅追问阻塞项，接受多参数输入 | 新纠正使旧信息失效时重核相关字段 | “几点提醒？” / 重问全部已知信息 | 有效字段保留 |
| U02 | 未输入、误识别、歧义或越界 | 选择对应恢复策略，连续失败改变提示 | 退出次数待配置 | 两个候选供辨别 / 原句反复播放 | 不形成无出口循环 |
| C01 | 执行动作前 | 按风险、歧义和可恢复性选确认 | 业务强制确认优先 | 高影响发送前核对接收人 / 无确认发错对象 | 确认策略与业务依据明确 |
| C02 | 已确认关键参数改变 | 将确认绑定新值，重判是否确认 | 未改变字段保留 | 更新日期后重判 / 沿用旧金额授权 | 实际执行值与有效授权一致 |
| T01 | 用户发声或停顿 | 区分停顿、附和及有效打断 | 判定能力未知时列依赖 | “嗯”按语境继续 / 任意声音停播 | 带标注音频案例验证 |
| T02 | 已接受打断 | 停止过时输出，续接新意图并修复播放上下文 | 已完成业务动作需保留和核实 | 被打断后接用户纠正 / 继续播旧答案 | 旧音频不恢复，续答基于已播内容 |
| T03 | “别说了/取消”等 | 区分停播与任务取消，歧义时按情境澄清 | 明确“取消提醒任务”无需无意义反问 | 停播后核对进行中的动作 / 停播即宣称撤销 | 播放与任务状态分别核对 |
| A01 | 反馈进度或结果 | 依据权威状态描述受理、执行、完成 | 结果未知须明示核实中 | “还在确认是否设置成功” / 超时后说已完成 | 成功话术有成功凭据 |
| A02 | 超时、重复请求、重试 | 结果未知先查状态；避免重复副作用 | 无查状态能力时提供人工/其他核对路径 | 核对原操作再重试 / 立即再建一条 | 最终对象数和状态符合意图 |
| A03 | 纠正后的旧结果迟到 | 核对关联任务；抑制过时播报并处理实际副作用 | 有效已执行动作不能仅丢弃回调 | 旧提醒已建则按授权修改或清理 / 假装旧操作从未发生 | 新目标正确，旧对象处理明确 |
| W01 | 长等待 | 按需真实反馈，定义新问题与离开后的任务去向 | 不固定填充间隔 | “还在查询，你也可以先问别的”仅在支持时用 / 虚构进度 | 信息真实，任务可追踪 |
| R01 | 失败或退出 | 保留有效上下文，提供支持的下一步 | 需清理的数据按产品策略处理 | 保留时间再尝试 / 让用户全部重说 | 恢复成本与退出去向可核对 |
| M01 | 语音与屏幕协作 | 重要结论可听懂，复杂细节用可用通道补充 | 产品场景明确要求看屏时说明 | “有三项，先读第一项” / 只说看下面 | 无屏主路径可用或限制明确 |

## 附件 B：三个状态轴
会话：空闲、收听、理解/澄清、回复、等待、结束。任务：未提交、执行中、成功、明确失败、结果未知、取消中、已取消。播放：未开始、播放中、停止中、已停止、已播完。

这些是设计词汇，实施时可映射现有状态；不要为套用规范重构系统。每个功能列出关键事件前后这三个轴的变化。用户停止播放时，任务可能仍在执行；任务成功后确认语音可能尚未播出。

## 附件 C：度量定义
| 指标 | 起止或分母 | V0.1 使用方式 |
|---|---|---|
| 首次实质响应时延 | 人工标注用户有效结束点→首段实质内容可听起点 | 与首次填充语分开，按场景报样本数、P50/P95 |
| 打断停播时延 | 用户有效打断起点→设备旧音频实际停止 | 同时报有效打断识别率，漏检单列 |
| 过早截断率 | 用户尚未结束却被系统抢答的轮次/标注未结束案例 | 犹豫、慢语速分别统计 |
| 误打断率 | 附和或环境音触发错误停播的案例/对应标注案例 | 附和与噪声分桶 |
| 任务完成率 | 达到用户预期结果的任务数／本期支持范围内已发起的任务总数，以实际业务结果核验 | 保留用户主动放弃、外部服务失败和结果未知，分别报告原因；不以排除失败缩小主指标分母 |
| 修复负担 | 完成任务额外要求用户纠正或重述的轮次 | 与失败原因一起分析 |

目标值待目标设备及样本基线确定。文本走查验证流程和规则；音色试听验证可听表达；设备音频验证轮次与时延；真实业务回执验证最终动作。每层单列状态，未执行写“未测”。
