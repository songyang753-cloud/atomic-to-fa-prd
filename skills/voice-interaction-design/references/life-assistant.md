# 生活助理子Agent交互规范与首批样板 V0.1

第一阶段用户已确认：提醒、日程、查询、代办。本文暂将“代办”解释为待办事项管理；替用户预约、购买、对外发送等代执行能力需独立定义业务与确认策略。适用产品配置V0.4及子Agent交互规范V0.1。以下为产品设计基线，接口与真机行为待验证。

## 产品目标与服务划分
用户在行走或双手占用时，通过耳机说出生活安排，能够记录、找回、调整，并在适当时机获知结果。首期优先完成语音闭环；拍照和GPS按任务所需采用，不作为每次调用的前置条件。

提醒、日程、待办是三类业务对象，可以由一个或多个FA提供。PRD先明确对象和服务归属，具体FA数量沿用平台能力，不为概念分类额外拆Agent。主Agent负责理解、续接和组织回复，FA负责业务规则和执行，OS负责授权、设备能力与交互编排。

| 对象 | 用户意图 | 成功标准 | 与其他对象关系 |
|---|---|---|---|
| 提醒 | 到某时间或条件告诉我一件事 | 规则真实生效，可查询、修改、停止 | 提醒触达后是否自动结束按规则，事情完成需另有依据 |
| 日程 | 在时间段安排活动 | 活动、起止和必要参与信息正确 | 提醒为可选属性；对外邀请属于额外动作 |
| 待办 | 记下需要做的事 | 事项可找回并标记完成 | 可有截止时间；截止时间本身不自动创建提醒 |
| 查询 | 获取安排或生活信息 | 回答有来源、范围与必要时效说明 | 查询默认只读，后续创建需明确意图 |

## 统一交互规则
### 时间与对象理解
相对时间以执行时的可信当前时间及用户有效时区解释。跨午夜、跨时区、过去时间、上午下午歧义按实际上下文核对；语音确认突出具体日期和关键时间。日程有开始和结束，待办可只有截止日期，提醒需要可执行的触发条件，三者不能机械共用必填字段。

“每周一”需明确循环规则，变更或删除循环对象时区分本次、此后和全部。“周末”若无已批准默认含义且影响执行，先澄清。全天活动与定时活动采用不同时间语义，不擅自把全天活动设成午夜提醒。

“这个”“刚才那个”“改到四点”绑定当前明确业务对象。多个候选时读出最少可区分信息再让用户选择。用户说“记一下”时根据内容判断，无法确定提醒、日程或待办时问一次；不能同时创建三个对象作为保险。

### 确认、执行与修改
建议普通个人低风险事项在参数充分时直接执行并反馈，具体由业务确认策略批准。批量删除、对外邀请/发送、共享及其他高影响动作需明确对象与影响后确认。

创建确认须有权威成功结果；未知时先核对原操作。用户重复原话不立即重复创建，但明确说“再建一个”可构成新意图。仅按文本相同去重会误伤合法重复事项，应结合任务上下文、操作标识及业务对象判断。

普通补字段沿原task续接；缺权限导致FA失败时保留需求为待办，授权后由用户重试重派。创建完成后的修改是新操作任务，引用原业务对象；task关联按平台支持情况。修改失败时说明原对象实际状态。取消创建任务、删除已创建事项、停止循环提醒、标记待办完成分别设计，避免混用。

### 查询与结果表达
先说与目标最相关的结论，列表分批读，保留稳定的候选指代和继续入口。“今天还有什么”要明确查询范围和时间窗口；跨多个来源仅在已授权且具备聚合能力时覆盖，缺少来源时说明本次查到的范围。

天气、营业状态等动态信息给出必要时间地点与来源限制。用户问“帮我安排一下”时先形成可理解建议，实际写入、冲突调整与对外通知按各自授权处理。日程重叠先说明具体冲突，不能自动挪动原活动。

### 主动提醒与任务结束
“设置成功”依赖规则生效；“提醒已发出”依赖投递记录；用户是否听到需播放或交互证据。业务成功和触达状态分别验收。

到点内容按敏感性、有效期和OS编排规则呈现。摘下、通话、勿扰、断连时采用平台支持策略，不默认外放。错过后是否补提醒由业务明确，过期事项不机械补播。用户说“知道了”“稍后提醒”“完成了”分别对应确认获知、重设触发和业务完成，模糊时澄清；无回复不能推断事情完成。

对话结束保留实际已创建对象。位置提醒属于扩展分支：需持续监测、规则生效和触达能力，首期时间提醒可先独立验证。拍照记录纸质日程需先识别、核对关键字段，再按确认策略写入；识别出文字本身不自动创建日程。

## 样板一：个人时间提醒（首个完整PRD建议对象）
用户目标：双手占用时快速设置一次性提醒，并可自然修改。

主流程：主Agent提取时间与内容→仅追问阻塞字段→提醒FA创建→核对权威结果→反馈时间和内容。到点后由真实提醒机制触发，FA给出通知意图，OS编排触达。创建闭环与到点闭环分别验收。

对话：
- 用户：“明天下午三点提醒我带文件。”
- 系统：（成功后）“已设好，明天下午三点提醒你带文件。”
- 用户：“改成四点。”
- 系统：（明确原对象，新修改操作成功后）“已改到明天下午四点。”
- 到点：“提醒你带文件。”
- 用户：“十分钟后再提醒。”
- 系统：（新触发真实生效后）“好，十分钟后再提醒你。”

无修改接口时说明实际限制；原结果未知先核对。提醒已触发后延后，需明确原触发的处理及新规则，避免两个有效触发。首版业务需确定：时间来源、创建/查询/修改/删除、重复保护、触发与投递证据、延后规则及隐私路由。

## 样板二：个人日程
用户：“明天下午三点到四点安排项目复盘。”参数充分且策略允许→查询已支持的冲突信息→发现冲突则说明具体活动并询问仍安排还是换时间→用户选择后写入→成功反馈日期、时段及活动。

“约小王一起”涉及联系人、参与人、共享及邀请发送，另行确认对象与动作；个人创建成功和邀请发送状态分别表达。“改成四点”若影响结束时间，按已批准保留时长策略处理并反馈新时段；没有策略时追问结束时间。不得擅自覆盖既有冲突活动。

## 样板三：待办事项
用户：“记得买牛奶。”若入口和上下文不足以判定对象，问“先记成待办，还是到时候提醒你？”选待办→创建→成功后“已加入待办：买牛奶。”

用户：“周五前买。”补截止日期；是否设置提醒另按明确请求或已批准偏好。用户：“买好了。”匹配明确对象后标记完成，成功再反馈。存在“给爸妈买”和“自己买”两条时先消歧。完成待办后关联提醒是否停止须有业务定义，不能默认跨FA同步删除。

## 样板四：安排查询
用户：“我明天有什么安排？”→按有效时区确定明日窗口→查询获准的日程来源→先概述数量与关键时段→分批展开→用户可问“第二个几点结束”。没有安排、查询失败、只获取部分来源分别反馈。

用户随后“那个取消了”先结合对象、语气判断是在陈述还是发出删除指令，含糊则确认；选定对象后进入对应业务操作。查询期间创建、修改的结果迟到时不混入旧列表；需要刷新时说明当前结果。

## 附件：首批验收预期
以下均为待执行设计用例。

| ID | 条件 | 预期 |
|---|---|---|
| LA01 | 完整普通时间提醒 | 一个正确生效对象，成功后反馈 |
| LA02 | 缺时间，一次补时间和新内容 | 只问缺项，两个字段同时采纳，沿原task |
| LA03 | 午夜边界、时区变化、过去时间 | 使用可信时间，歧义先核对 |
| LA04 | 创建超时后重复说原话 | 先核对，无意外重复对象 |
| LA05 | 创建在途纠正及旧结果迟到 | 追踪原操作，最终对象符合最新明确意图 |
| LA06 | 创建完成后修改失败 | 新操作有结果，准确说明原对象 |
| LA07 | 循环事项修改/删除 | 明确本次、此后或全部 |
| LA08 | 日程冲突与不明确结束时间 | 不覆盖原活动，按策略处理时长或追问 |
| LA09 | 个人日程带对外邀请 | 写入与发送分别确认和记录状态 |
| LA10 | 待办带截止日，无提醒意图 | 不擅自创建提醒 |
| LA11 | 完成待办，有同名候选 | 消歧后完成正确对象，关联提醒按明确规则 |
| LA12 | 部分日历来源查询失败 | 说明范围，不声称已查全 |
| LA13 | 到点时摘下、通话或断连 | 按隐私路由与时效处理，保留触达状态 |
| LA14 | 稍后提醒与没有回应 | 延后规则可追踪，无回复不当作完成 |
| LA15 | 缺权限与普通追问 | 分别采用失败重派和原task续接 |
| LA16 | 拍照导入或位置提醒 | 数据、授权与能力满足后执行，缺口不虚报成功 |

首期建议先以一次性时间提醒跑通创建、修改、触发、触达四段，再验证日程、待办与查询；循环、共享、位置触发及拍照导入按实际业务范围追加。建议顺序是设计落地路径，不构成已确定的版本承诺。
