# 原子能力 → 纯语音 FA PRD

## 不变的产品与交付边界

- PA 是 AIOS，MA 是 PA 内部主 Agent，FA 是 PA 外的业务服务。统一用 PA／FA，用户经 PA 说话、确认和接收结果，FA 处理业务；产品没有 UI。
- 本期功能必须由用户给定的原子能力与指定 PA 基线支撑。PA 位置、思考、用户记忆只按用户说明使用；精度、读写接口、播放回执、权限、后台通知等未说明契约标待核实。本期外部业务动作必须映射到用户提供的具体工具／命令／端点及所需 PA 能力；FA 派生处理映射真实输入字段、可复现规则与结果边界，不要求虚构专用接口，并说明输入从何取得、返回如何支撑下一步；组合功能逐步核对。缺少必要能力的功能移入附录，不列为本期可实现功能；有定义但未实测的能力如实标注验证状态。
- 安全查询实际调用并保留脱敏回执；按副作用判断，不按工具名称或 HTTP 方法。下单、支付、取消、发送、删除等实际操作未经用户明确授权不执行。能力状态区分定义已读、查询已验证、历史证据重放、真实链路待验证、失败；状态不得混写。
- [六章模板](references/prd-template.md)是交付形式正本，不因专家数量增加正文章节。两张图分别为用户流程、用户／PA／FA／外部服务协作流程，必须美观简洁、飞书原生节点可编辑。正文简洁，独立讲清方案和关键边界；不放调研／验证过程总述、泛泛的价值待验证提醒或重复说明，影响用户决策的实际限制直接写清；AI／研发细节、证据、合同、评审记录进附录。研发须读同版正文及附录。
- 固定五项指标与口径：意图 Precision、Recall 各≥95%，首词 P50≤1秒／P95<1.5秒，有效答复时延按任务校准，任务完成率≥90%。均为建议目标，实测值另列；首词从用户实际说完到设备开始播放，包含整个 PA／FA 链路。
- 默认连续生成，不要求用户逐项确认需求。默认新建已授权的飞书空间；仅用户明确指定才更新已有文档。用户要求仅研究／本地稿时遵从该范围。

## 主持职责与独立专家

先读 [协作与验收合同](references/agent-collaboration.md)。你是主持者兼产品负责人，亲自完成能力边界判断、方案取舍、正式稿收敛与交付；不得只派单。每个专家实际由独立 Agent 执行，先读其 SKILL.md，不以主持者换称谓模拟多人评审。

| 专家 | Skill | 主要交付 |
|---|---|---|
| 懂技术的产品角色 | `fa-capability-analysis` | 全量能力台账、业务组合验证、需求机会、功能可实现性及四阶段复验 |
| 调研专家 | `fa-domain-research` | 领域任务、同类产品、交互与指标结论、可迁移及不采用机会 |
| 产品专家 | `fa-product-design` | 需求与功能、优先级、逐功能行为、完成终点；先不设计完整交互 |
| 交互专家 | `voice-interaction-design` | 同版节点、话术、追问、确认、恢复、用例 |
| 独立评审 | `fa-prd-review` | 产品／技术／算法／交互视角分别审；业务视角按相关性激活 |
| 测试专家 | `fa-test-engineering` | 覆盖矩阵、统一用例、消费回执、执行证据、缺陷与回归 |
| 产品负责人 | `fa-product-owner` | 裁决、修订、受影响方重新验收、正式 PRD 与发布核验 |

独立 Agent 可互相交流、多轮提问。先让下游定义所需证据、字段和验收标准，再让上游交付；接受方实际消费文件并验收。并发仅用于不互相依赖的部分，前置验收失败先修复再推进依赖项。

## 执行顺序

1. **建立范围与交接计划**：保存用户约束、PA 基线、模板哈希、旧版映射、项目 revision；按信息保全合同冻结原始要求基线，并由独立下游反查来源完整性，逐条记录采用、合并、替代、暂缓或不适用。读取用户指定 AIOS 架构基线 （由使用者提供架构基线） 相关内容；未读到时登记，不编现状。由产品与交互专家先提出上游交付要求；所有角色采用 schema_version=4 的七角色结构化交接及哈希引用，旧版只作历史复查。
2. **能力与调研**：先执行 [文档尽调与四阶段能力验收](references/capability-gates.md)，建立 capability_validation 并绑定实际消费回执。能力专家按 `fa-capability-analysis` 的能力尽调参考全量盘点用户给定能力，验证业务组合并交付需求机会、可实现性矩阵和脱敏证据；必要安全查询实际调用。新领域首次深度检索、精读官方和可信来源；同领域复用已核研究并更新疑点与易变事实。研究结论区分事实、推断、假设；竞品功能只是需求线索。能力专家可要求研究补证，研究不得替能力专家宣布接口可用。
3. **生成产品需求**：产品专家执行 [需求发现](references/requirements-discovery.md)，按原子能力及加工、高频任务、跨能力场景编排、开发者文档与示例四路发现，使用 discovery_version=2；从用户任务向下检能力、从能力组合向上挖需求；保留稳定 F 编号和新增／合并／舍弃依据。运行 `scripts/check_discovery.py` 并进行语义检查。项目明确暂缓的首次认证、个人信息需求保留现状，不新增设计与用例；未暂缓时，首次认证／授权（手机完成）与个人信息获取／复用／保存作为两个独立需求设计；必要能力缺失时记录缺口与影响，不承诺本期可实现。个人信息按字段依次向 PA、用户提供的 MCP／CLI／API 获取，仍缺失再询问用户；长期保存和账号绑定须有明确能力及授权支撑。能力专家验收每项功能的输入来源、能力组合与结果依据。产品负责人冻结工作基线后继续，不等待用户清单确认。需要展示时给四列清单：功能名称、用户需求、能力依据、优先级。
4. **设计语音交互**：读 [交接合同](references/handoff-contract.md)，交互专家实际读取产品交接包，按 `voice-interaction-design` 指定参考设计。新增业务需求或后果变更提给产品负责人裁决；负责人可在能力范围内自主调整，同步依赖交付件并让受影响角色重新验收。范围、版本、优先级、规则不得悄悄漂移。能力专家复验提问、确认、修改、恢复与结果播报的能力依据。手机认证是配套流程，FA 本体仍为纯语音，不因此新增 FA 页面。
5. **收敛与评审**：调用 `fa-test-engineering`，由独立测试专家基于产品预期生成/补齐覆盖与用例，产品、能力和交互专家验收后由负责人冻结；按 [统一 query 与测试用例规范](references/query-test-corpus.md)冻结业务预期与禁止动作；产品定义目标、能力审核可执行动作、交互补齐事件和节点、独立评审检查预期。能力专家复验测试预期与真实输入输出、禁止动作一致，并在正式稿收敛时核对正文、附录及两图中的能力承诺；差异触发相关交付件更新和重验。负责人按固定模板整合正文与附录，两图投影同一业务状态与转移。用例为唯一机器正本，独立飞书测试表由它生成、链接放附录；按功能、规则和流程分支覆盖扩充用例，再补语言泛化，单轮泛化与多轮状态覆盖分别报告。产品、技术、算法、交互由独立 Agent 分别评审；CEO、CFO、COO、运营按实际价值、成本、履约与运营问题决定是否加审并记录原因。最多两轮修复／复审，修改后评审必须绑定最新内容与哈希。事实和能力约束不能被投票覆盖；文档矛盾、越界承诺必须修复。未实测业务／PA／设备／性能可明确列为验证依赖，写影响、限制、方法和责任，不能称上线就绪。
6. **测试消费与研发验收**：按 [测试执行合同](references/test-execution.md) 调用 `fa-test-engineering`，让独立测试 Agent 实际消费同版交付件，先给 intake，再按可用入口执行并回写证据；无真实入口标 blocked，模拟与真实实现分开。关键规则逐条登记责任、检查条件、拒绝行为、正负用例及实现证据；缺实现时保留研发验收阻塞，不影响如实交付设计。修改影响到预期时由负责人裁决，受影响角色重新验收。
7. **飞书交付**：必须读并调用 `lark-doc` 创作流程、`lark-whiteboard` 作图流程及 `lark-sheets` 独立测试表流程。官方 `lark-cli --profile <your-profile> ... --as user` 新建，已有资源不动；工具不可用时如实报告阻塞，不用图片或 Mermaid 代码块冒充可编辑画板。正文、附录、必要研发附件一起发布。同时创建独立飞书测试表，附录链接真实 URL，检查各 sheet 的用例 ID、行数、版本和内容与机器正本一致；用户要求本地稿时均不写远端。
8. **同版回读与终审**：完整 fetch 正文、表格、链接与两图 token；导出两图原始节点和实际预览，逐图核文字、分支、连接及布局，确认文字／形状／连接均为原生节点。最终评审核全篇与图一致、范围全覆盖、纯语音、五项指标一致、无凭据。保留真实 URL 和回读凭证，提供简短结论与验证边界。

## 校验与维护

项目交接检查用 `python3 scripts/check_collaboration.py <project>/collaboration.json`；原有产品／交互 JSON 用 `scripts/check_handoff.py`，发现包用 `scripts/check_discovery.py`；统一用例用 `scripts/check_cases.py <project>/corpus.json`；测试执行与关键规则验收用 `scripts/check_execution.py <project>/execution.json [<project>/acceptance.json]`。缺陷关闭另用 `fa-test-engineering/scripts/check_defects.py` 核验修复版重跑回执。机械检查只验结构及可枚举约束，独立语义评审、实际查询与原生文档回读仍须执行。关键规则必须有具体验收；主动破坏混版、范围、授权失效和未知结果恢复，确保相应检查报错。

借鉴 SYBuilder（`product-flow`）的稳定 ID、双向交接和可证伪收敛，不继承其 UI／原型／上线流程或 PRD 目录。只按需读它的相关阶段，不自动安装 skill。共享正本放 `~/.agents/skills`，Codex、Claude 均须可发现；改后跑官方 quick_validate.py、断链检查与反例测试，正文模板分区哈希保持不变，附录允许按授权增补并记录差量。

迭代与回归同时执行 [变更及行为回归规范](references/change-and-regression.md)：归档旧版、记录行为差量、独立控制任务、按边核两图、受影响角色复验。新增证据与 AI 研发任务放附录；本地回归不触发飞书写入。

跨阶段交接必读 [信息保全与消费检查](references/information-continuity.md)，生成 continuity.json 并执行 `python3 scripts/check_continuity.py <project>/continuity.json`。它引用既有交付件和规则，不另建业务预期；只通过结构检查不能宣布语义无遗漏。

当前项目最终检查统一执行 [项目验收入口](references/project-gate.md)：`python3 scripts/check_project.py <project>/project.json`。它强制串联现有检查并校验同版引用；旧格式仅供历史复查。独立语义评审必须回查原始要求及具体图边、用例和正文，不能用结构通过替代内容验收。
