# 统一 Query 与测试用例集

本规范只补充协作机制与 PRD 附录，六章正文、四列功能清单、五项指标和两张原生可编辑流程图保持原样。用例服务于需求发现、交互设计与研发测试；一批语言变体不能替代任务、边界和状态覆盖。

## 一份正本，多个可读视图

项目保存 `corpus.json` 清单与 `cases.jsonl`（每行一个完整用例）作为同版测试正本。交互合同原有 cases 以稳定 ID 引用/投影视图保留兼容，禁止另写互相冲突的预期。PRD 附录放测试范围、覆盖缺口、执行状态及正本入口；飞书交付时测试集必须单独发布为飞书电子表格，附录放真实链接、版本及覆盖摘要，完整用例留在表格中。正文不新增 Query 章节。

飞书表格使用两个 sheet：`标注query`、`泛化query`。由同版正本生成，均保留 query、action 两个基础字段，并扩展 case_id、上下文、预期结果、禁止行为、功能/规则、执行状态；query 为用户原话，action 为可观察的预期动作，不能只有意图标签；完整版事件与证据通过 case_id 查正本。不是仅有 query/action 两列的无上下文意图清单。另有覆盖/执行记录时使用独立视图，避免手工维护第二份预期。发布后回读表头、行数、稳定 ID、关键预期、链接和版本；本地任务仅保存待发布视图，不写远端或虚构链接。

## 最小结构

`corpus.json`：
- `schema_version: 1`、`revision`；可加 `corpus_version` 表示同一业务版本的测试扩充。
- `sources`：`handoff`、`interaction`、`flow_source`、`body`、`appendix`，每项 `{path, sha256}`。路径相对清单目录；正文和附录不嵌入清单哈希，避免循环引用。
- `cases: {path, sha256}` 指向 JSONL。
- `oracle: {owner, frozen_at, basis}`：谁依据哪些已定需求/规则冻结预期。应在执行模型输出与评分前冻结；修改预期必须记录原因并独立复验，不能为通过测试回填答案。
- `coverage_exceptions`：可选 `[{kind: feature_ids|rule_ids, id, reason, owner}]`。例外须说明当前影响，关键规则缺口保持为未关闭问题，不将“有例外”汇总为全部验收通过。
- `coverage.required_flow_edges`：可按图 kind 列必须覆盖的 `{source,target,label}`，至少由负责人和交互评审选取确认、修改失效、未知恢复、取消等业务相关关键边。机械检查只检查声明的边，完整边/分支语义覆盖仍由独立评审核对。

每行用例：

| 字段 | 要求 |
|---|---|
| id、revision | 稳定唯一 ID，同版；保留旧例去向 |
| kind、semantic_family、split | `annotated` 或 `generalized`；同一语义种子/改写家族只能在 `dev` 或 `test` 一侧 |
| feature_ids、rule_ids、node_ids | 引用已有功能、适用关键规则、交互节点；无适用关键规则时 rule_ids 可空 |
| flow_nodes | `user-flow`、`business-flow` 分别列图节点 ID，至少与本例交互节点有投影交集。抽象图未表达的专用修复写 `flow_exemptions: {图kind: 原因}`，不硬造映射 |
| flow_edges | 可选，按图 kind 列本例走过的 `{source,target,label}`，须存在于图源，且两端均属于本例该图的 flow_nodes |
| context、query、events | 非空上下文字典、用户原话、按序事件数组；包含已有对象、版本、授权和服务返回等实际必要条件 |
| expected | `{actions: [{capability_id,min_calls,max_calls,target}], outcome: 可观察结果}`；纯语音答复 actions 可空，业务动作必须引用本例功能允许的能力 ID，明确次数与对象 |
| forbidden_effects | 非空数组，描述本例禁止的副作用或错误承诺 |
| verification | `{method,status,evidence}`；实际写操作另须明确授权来源与范围 |

method 必须按实际执行通道记录：mock、历史回放或安全查询的证据只支撑对应通道，实际写入需要 live-write 与明确授权，不能将前者改名冒充写入已验证。通道与证据内容是否相符须由独立评审核实，机械检查只验证字段、引用和哈希。

验证方式 `method`：`design`、`mock`、`evidence-replay`、`live-query`、`live-write`、`device`、`performance`；执行状态 `status`：`not-run`、`pass`、`fail`、`blocked`。设计样例统一 `design/not-run`；设计评审通过记在独立评审记录，不改成执行 PASS。历史证据重放保留原时间；通过模拟仅说明对应模型/程序的所测行为。设备和性能必须有相应设备/计时证据。实际执行 pass/fail 的 evidence 至少引用真实 `{path,sha256}`，具体执行对象、实际动作、结果与判据写入证据文件；文件存在与哈希一致仅说明可追溯，不证明结果正确。

## 从需求到回归

1. 产品专家先交功能、关键规则和可观察终点，并提出测试分类。交互专家把每项规则落到动作、恢复和节点；测试预期独立从冻结规则推导。
2. 先建立“功能 × 适用条件／规则 × 流程分支”的覆盖矩阵，再生成测试；每项功能覆盖正常完成以及所有适用的缺信息、纠正、放弃、结果空、权限与能力不足、服务失败及恢复。每条关键规则和关键图边都有可定位用例；不适用项写原因，缺口保持开放。高风险提交还要逐一验证每个执行前提缺失、修改后旧确认失效、重复／迟到事件、对象歧义及结果未知的恢复，按真实风险补组合场景。纯查询可直接结束，不能强迫进入交易。数量随独立场景和分支扩充，不以任意总数或批量改写替代覆盖；分别报告标注／泛化用例数、独立场景数及剩余缺口。
3. 必备上下文对按风险选择：同一句“确认”配当前/旧版摘要；“不要了”配草稿/已提交；同名对象配唯一/多个目标；未知结果配有/无合法标识。增加口语、省略、指代、连续修正与范围外表达。语音识别错误和噪声数据需要音频来源，不用文本改写冒充真实语音测试。
4. 泛化保留业务语义及预期，仅改变表达；会改变对象、授权或结果的变化必须成为新场景。按 semantic_family 划分 dev/test；评估前封存 test，避免同时用同族改写做开发与评估。
5. 下游测试消费者实际读取正本，核验可执行前置、明确判据、对象及动作次数；不能执行的标阻塞并写缺口。独立评审核需求→规则→交互→两图→用例→正文/附录，再反查每个动作的能力依据。缺陷由产品负责人裁决，修改后更新受影响源、预期及投影视图并重新验收。
6. `python3 scripts/check_cases.py <corpus.json>` 检查版本、源哈希、ID、声明覆盖、能力动作、两图节点/边、语义家族分割与验证状态。负例应主动破坏：旧版源、漏功能/规则、伪造 PASS、未知能力、错误图边、跨 split 同族、无授权真实写入。语义错误还需独立评审或行为执行检出，字段全齐不能替代它。

执行报告分开列出：结构校验、独立语义评审、事件模拟、历史回放、当前安全查询、实际交易、PA/设备、性能。未执行层保留 NOT-RUN；本轮没有真实交易授权时可完成文档和测试设计回归，产品真实履约与时延验收继续待验证。

## 测试执行补充

独立测试消费者按[测试执行与研发验收合同](test-execution.md)提交同版 intake、execution.json 和 acceptance.json；结果回链统一 case ID。缺真实实现时保留阻塞，修复后重跑受影响用例，由负责人和独立评审收敛。正文与远端交付形式不变。
