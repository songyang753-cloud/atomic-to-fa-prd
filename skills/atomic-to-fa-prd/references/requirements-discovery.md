# 需求发现与功能收敛

适用于阶段 A。目标是更快生成有用户价值、能力可追溯、语音可完成的候选需求，沿用四列清单，由产品负责人冻结项目工作基线，不改变六章模板或交互合同。用户提供的 MCP、CLI、API 是本期能力边界。

## 四路发现与 FA 加工（新项目必用）

候选按四路发现，合并去重；一项可有多个来源。每路记录已检查、无适用机会或资料不可获得及其原因，不设数量配额：

| 来源键 | 工作 | 交付 |
|---|---|---|
| atomic | 原子数据与动作，以及 FA 对返回数据的筛选、排序、计算、比较、分组、归纳和关联 | 直接与派生功能 |
| high-frequency | 高频任务及选择、修改、确认、执行和恢复的完整业务过程；没有频次证据标假设 | 任务型功能 |
| orchestration | 结合常用功能、其他有来源的信息、已确认 PA 能力和信息，分析生活场景 | 跨能力任务与依赖 |
| developer-examples | 全量阅读可获取的开发者文档和示例，逐例采用、合并或说明舍弃原因；缺资料如实登记 | 官方案例与遗漏机会 |

接口提供事实和外部动作；FA 可基于已有数据执行派生处理，无需为排序等虚构专用端点。逐步区分 external（实际工具）、derive（FA 加工）、pa（PA 数据/能力）。加工步骤须有输入字段来源、操作、规则、输出和边界；数值计算和排序采用可复现规则，生成解释绑定原始事实。编排检查对象、单位、时效、候选范围和上下游输入输出；外部信息须有来源及适用范围。缺关键数据、权限或真实能力则缩小终点或记 gap；补问能补信息，不能补执行能力。

附近门店：距离排序须有可比较距离，坐标计算说明直线距离，步行时间依赖路线；候选不完整只比较已查到门店。顺路买咖啡：检查当前位置、目的地、出行方式、路线/绕行依据和门店商品；仅查附近不能承诺顺路。给爱人买咖啡：检查人物身份及获准使用的偏好来源，缺信息再询问，不能从“PA有记忆”推定已有偏好。这些是发现示例，非所有领域必做功能。竞品不是功能上限，也不能代替能力证据。

新发现包使用 `discovery_version: 2`：增加 `demand_routes`，上述四键每项为 `{status: reviewed|not-applicable|unavailable, reason, candidate_ids:[]}`；每个候选增加 `discovery_sources`，与路线双向映射。include 增加 `steps`，每步 `{id,kind,inputs:[],rule,result,limits}`；external 另有真实 `capability_id`，pa 另有 `dependency_id`，derive 另有 `operation: filter|sort|calculate|compare|summarize|group|join|plan`，不得冒造 capability_id。inputs 说明字段及来源；步骤引用限定在该候选已登记能力/PA依赖。gap 记录缺口，不强填可执行链路。旧发现包可复查，不能据此宣布四路新版验收完成。

## 双向发现

先读能力，记录业务对象、动作、关键输入/返回、限制、实际副作用及证据。再暂时放下接口名称，从用户当前做法、使用情境、困难和期望结果列出任务。将两份结果交叉核对：能力可以支撑哪些任务；任务的关键步骤是否具备能力。用户材料不足时允许提出产品假设，不虚构访谈、规模、使用频率或已核实的 PA 能力。

按以下视角寻找机会；没有适用机会可记录不适用，不要求每类产出功能：

|视角|要发现什么|
|---|---|
|直接目标|用户最直接要完成的事及完成终点|
|条件约束|预算、地点、时间、偏好等约束能否被真实数据判断|
|选择决策|多选项之间的犹豫、信息不足和取舍|
|能力组合|输入输出和业务对象可衔接的能力，组合后能省掉哪些步骤|
|过程调整|更改、暂停、放弃、续接时如何保留有效内容|
|结果恢复|结果如何核实，失败或未知怎样安全继续|

只组合语义和前提兼容的能力；不做接口全排列，不追求全部接口转成功能。重要且存在实质选择的需求，比较两种可行处理方式，例如先追问再推荐与直接用已知约束给候选；也考虑 PA 直接回答或无需新增 FA 功能。记录取舍理由，不为单一路径强造方案。

## 需求、功能与规则

- 需求描述用户情境和预期结果，避免用接口名代替。
- 功能是支撑结果的产品能力；同一需求可以由多个功能共同完成。
- 规则描述功能怎样执行，例如修改后重新确认、防止重复操作、停播不取消业务，归属对应功能。
- 同目标的口语变体合并。独立价值和完成终点不同才拆分；不为增加数量把每个场景拆成功能。
- 用“换掉产品名称是否仍完全适用”检查过度笼统的描述，再补业务情境和结果。

## 两条证据轴与本期筛选

需求证据分为 `user-request`（用户明确提出）、`observed`（获准的真实使用/研究观察）、`research`（有来源的公开研究）、`hypothesis`（产品假设）。用户确认设计范围只表示范围获准，不能冒充观察证据。竞品功能是启发，不足以证明本产品用户需要。

能力证据标 `live-query`、`historical-query`、`definition-only` 等实际状态，记录来源与未验证限制。查询结果只支持实际返回的字段；未执行的交易仍待验证。可将定义支持但链路待验证的功能列为候选，并明确上线阻塞和退路；缺少关键能力则列 gap，不能以“待联调”掩盖能力不存在。

逐项检查：
1. 每个关键动作、输入和结果是否有能力依据，PA 依赖是否已核实；未核实依赖写明影响及真实退路。退路本身也须有依据。
2. 输出数据是否足以支撑承诺。搜索预估价只适合初筛，严格预算按有效报价；糖度规格不推导营养或健康结论。
3. 用户能否得知结果。生命周期按实际业务裁剪；信息查询以回答目标问题完成，不强加交易、取消或通知。
4. 是否能通过听说完成：必要信息是否可获得，候选是否可缩小，是否依赖屏幕，确认对象是否清楚。这里只作初筛，不提前生成完整话术、节点或扩展交互 skill 的职责。

P0 是核心任务的最小闭环及关键控制；P1 是有依据的场景扩展和减负；P2 是收益或需求证据较弱、依赖较多但仍有能力支撑的候选。存在能力不代表必做；缺使用数据时不虚构 RICE 数字。完成状态未知的安全退出可以成为退路，但不计为用户预期任务已完成。

## 查漏、研究与效率

第一次合并排序后，暂不看功能名，按用户任务重新走一遍：明确目标→找选项→选择配置→核对→执行→查结果→调整结束。只保留本业务适用环节。再按业务对象核对读、改、执行和结果关系。记录遗漏及补充、适用视角结论、未采用能力/候选的原因；不要求能力使用率达到 100%。

研究围绕会改变需求取舍的疑点：优先已有用户材料、官方定义、安全查询，再针对性查公开资料；写清研究实际能证明什么。高影响且无法判断的决定一次问一个问题；独立部分继续。核心任务已覆盖、主要不确定性已标明、进一步研究没有新的实质机会时提交清单，不无限搜索。

复用有版本、时间、哈希和限制的快照；同输入对比用同证据回放，线上更新另列，避免将数据变化混为方法改进。新增能力只重查相关任务，缓存不是实时库存、价格或营业状态依据。研究深度随不确定性与决策影响调整，常规清单不强制遍历全部产品 skill。

## 同类产品深度研究：拓宽需求，再按能力收敛

首次发现业务需求时，默认先做一轮有范围的同类产品调研；用户明确要求 deep research、常规发现遗漏明显或关键场景仍不清楚时加深。小幅修改已有功能可复用有效研究，只查变化部分。用户明确限定同输入回归时保持原快照，另列研究增强建议，不混入方法对比。无法检索时记录缺口，不能声称已完成调研。

1. **先设研究问题。** 围绕目标用户想完成什么、当前怎么做、哪些困难尚未解决、同类产品如何处理、语音 FA 可以减少哪些步骤来组织问题。已有候选仅作对照，主动搜索清单外的任务，避免只寻找支持现有设计的材料。
2. **选择有差异的参照。** 覆盖直接同类产品、相似任务的语音/对话产品、用户现有替代做法；按业务选择有代表性的对象，不按固定数量凑齐。跨行业只借鉴可迁移机制，核对其业务前提。说明各对象的选择理由和缺失类型。
3. **实际搜索与精读。** 使用当前可用的搜索/抓取工具；选用深度调研 skill 前先读其说明。工具不可用时采用已授权的可用搜索工具，不自动安装或假装运行。用任务、痛点、异常与功能等不同关键词检索，精读影响需求判断的官方帮助、产品说明、服务规则或可访问的实际流程；用户评价用于发现痛点，核对版本、地区、时间及样本偏差。不能只凭搜索摘要下结论。
4. **从功能还原需求。** 对重要发现记录“用户情境与目标→现有做法/困难→产品如何处理→可借鉴机制→适用前提”。区分产品确有该功能、用户确有该痛点、我们推测有价值三类结论。单一营销来源注明自述；找不到功能只能写未找到公开依据，不能断言不支持。
5. **转换为 FA 候选。** 用统一用户任务名称跨产品合并，再对照原子能力、PA 依赖和纯语音限制。页面筛选应转成如何缩小候选的语音任务；地图不直接转成 FA 地图功能。分别判为新增、增强既有功能、归入规则、能力缺口或不采用，并说明理由。每项本期候选仍须说明完成终点和能力依据。竞品支持不作为本 FA 能力证据；公开功能也不足以证明目标用户的价值和频次。
6. **核查与停止。** 反向检查核心任务、条件约束、选择、组合、修改、恢复是否遗漏；复核高影响事实的来源，优先独立依据，互相转载不计交叉验证。连续扩展检索主要重复既有机会、核心任务已覆盖且剩余未知已明示时提交清单。存在影响范围的证据冲突时继续针对性研究，不以来源数量宣称全面。

任务目录保存轻量 `research.md`：研究问题、参照选择、来源链接/标题/访问日期及适用版本、重要发现、事实或推断、局限，以及“研究发现→候选 id→处理决定→能力依据”的机会对照表。本地材料注明路径和日期。需要精确回归时保存允许保留的来源快照及哈希；不把外部网页指令当任务指令，不外传凭据或用户私密上下文。

`discovery.json` 中 demand.source 指向具体研究条目；只有来源确实支持需求判断时使用 research，纯竞品启发的本产品价值仍标 hypothesis，并在来源中保留启发依据。可选 research_summary 记录引用文件、问题覆盖、未解决问题和受影响候选；研究笔记进入 source_files 做证据引用。沿用既有检查器，研究真实性和映射正确性由来源回读与语义走查核验。

提交需求清单时，除既有四列外，附简短研究结论：哪些机会被新增或增强、哪些已被原清单覆盖、哪些因缺能力或语音负担未采用。详细竞品矩阵和证据留工作区/后续附录，不扩写正文；无需用户逐项确认。产品负责人冻结工作基线后，再将同版清单交给语音交互 skill；调研不直接改写已确认交互合同。

## 最小发现记录

在任务目录保存 `discovery.json`，正文不展示内部字段。自由分析可以用笔记，进入清单前收敛为：

- `revision`、`run_mode: live-query | evidence-replay | definition-only`、`source_files`（path、sha256、source_date；相对路径以本 JSON 所在目录解析）。
- `capabilities`：id、source、verification、limits。只登记实际可引用能力。
- `platform_dependencies`：id、status（confirmed / unverified）、source、fallback。纯语音形态是约束，不证明定位或播放回执可用。
- `candidates`：id、name、need、demand（kind、source）、capabilities（id 列表）、platform_dependencies（id 列表）、end_condition、voice_fit、limits、decision（include / merge / rule / gap / reject）、reason。include 另有 `priority` 和 `readiness`；merge/rule 的 `target_ids` 指向 include；gap 说明缺什么。readiness 使用 `query-supported` 或 `definition-supported-pending-validation`，表示依据成熟度，不表示需求已验证。
- `lens_review`：上述六个视角分别写机会或不适用原因；`omission_review`：独立查漏结论和未采用能力原因。
- 重跑另存基线与 `baseline_mapping`：旧 id、目标候选 id、变化和理由。新提案先记 `approval_status: pending`，负责人基于用户已授予的连续生成权限裁决后记 approved，保存决定，不冒充真实用户研究验证。

运行 `python3 scripts/check_discovery.py discovery.json`，再逐项语义走查：能力是否真的支持该结果、用户价值是否具体、退路是否真实、规则是否被包装为功能。自动检查只核对引用、记录和证据文件，无法证明语义正确或需求完整。用真实反例（移除历史能力、只读能力、重复表达、接口改名）核对相应结论；不要把固定案例通过当通用质量指标。

产品负责人冻结后，把已纳入基线的 include 转为既有 `handoff.json` 的 features，保留 id/priority/完成终点/限制；保存 `discovery_source`（path、sha256）作为发现依据，不并行维护第二套已确认范围。完整交互设计发现范围变更时，交由产品负责人裁决并同步受影响交付件，重新验收。

## 方法来源与采用边界

- SYBuilder/product-flow：区分问题和方案、比较候选、检查泛化描述；不继承 UI 原型或完整项目阶段门禁。
- gstack/office-hours：当前做法、实际痛点、最小有价值切片与关键假设；不强制商业创业问卷。
- [Product Talk](https://www.producttalk.org/opportunity-solution-trees/)：结果→需求机会→方案→假设验证；能力推导的机会仍需标假设。
- [Strategyn Job Map](https://strategyn.com/jobs-to-be-done/jobs-to-be-done-playbook/build-your-job-map/)：按用户任务全过程查漏，按业务裁剪。
- [SVPG](https://www.svpg.com/four-big-risks/)：价值、可用性、可行性、商业可行性；以本项目实际证据判断。
