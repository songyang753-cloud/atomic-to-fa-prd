# 能力尽调与可实现性验收

## 全量盘点与业务理解

先接收下游交付标准，随后进行两遍研究：第一遍从官方文档与示例完整理解用户给定能力，第二遍根据下游疑点补查。先盘点相关开发者文档的导航／目录、入门指南、业务指南、接口／命令参考、错误与限制、官方示例，以及用户给定范围内的全部 MCP 工具、CLI 命令和 API 端点；对照实际发现列表、定义、schema 和必要源码。不要只按已经想到的需求选读接口。

文档覆盖清单逐项记录来源、版本或访问时间、适用范围、阅读状态、关键结论及关联能力。状态区分已读、无法访问、待补、不适用；未读条目必须有原因及影响。记录清单的枚举来源和覆盖边界；动态或无法完整枚举的目录列待补项，不声称全量完成。全量指本项目相关版本与范围，不要求阅读无关产品全部代码。全量阅读不意味着全量执行有副作用的操作。

每个相关官方示例记录来源及版本、展示的用户任务、前置条件、调用顺序、关键参数传递、结果／失败处理、可借鉴机会和使用限制。示例中的演示值不能当当前用户真实数据；示例与现有定义或实测返回冲突时，保留冲突并补证，不合并成未经证明的新能力。没有可用官方示例时明确记录搜索范围及缺失，不编造样例来源。

核对文档、示例与实际能力清单的差异：实际有而文档缺、文档有而当前入口无、版本不同或需要额外权限，分别记录。每项给定能力均有结论或明确覆盖缺口；每项相关文档及示例均有处理状态。产品与研究消费者验收这些底稿后再扩大功能承诺。

每项沿用项目能力 ID，记录业务含义、来源、输入必填性及来源、枚举／单位／默认值（以定义为准）、实际输出与状态、错误、账号／权限、前置条件、时效、分页及调用限制、操作影响和验证状态。未知项写明未知，不补造字段。将输入来源区分用户、PA、前序接口和业务配置，核实对象是否属于当前用户及同一业务上下文。

## 业务组合与需求机会

按“用户目标 → 步骤 → 具体能力 → 必要输入来源 → 可用输出 → 下一步”组织组合路径。检查对象标识、规格、数量、报价、状态和用户绑定能否衔接，用户修改引起的失效与重新查询，最终结果凭据，以及失败／结果未知的恢复路径。每步分别标明 PA、FA 与外部服务责任。

功能可实现性矩阵按业务动作记录功能 ID、能力 ID、必要输入及来源、可用返回、执行前提、结果核验方式、验证状态、证据引用和缺口。必要参数须能从已授权 PA、用户表达、前序结果或明确业务配置取得；“前一步返回了结果”还要核对标识、枚举、单位、有效期及业务上下文是否足够供下一步使用。必填输入来源缺失、依赖能力待核实或缺结果依据时，由负责人缩小范围、挂起受影响动作或移入缺口，不按可实现通过。

从已证实的组合提出机会，交付“用户任务机会、所需能力组合、可实现范围、缺口与限制”四项。调研专家的机会也须逐项核能力。产品专家决定价值和优先级；本角色不另建需求正本。历史复购须有历史订单或可用记忆并重新校验当前商品；最优价格须核候选范围和可比实际报价；写操作重试须核幂等和查询恢复；主动提醒须核状态来源及 PA 通知契约。没有支撑时缩小承诺或列缺口，不把搜索、预览或工具名称扩写为保证。

需求机会还应回链相关官方指南／示例和组合路径；仅由产品经验推断的机会单独标为推断。产品专家登记采用、合并、待核或不采用的决定及原因。本角色验能力事实，研究专家验用户／领域证据，产品专家验价值与优先级，三种结论分别保留。

## 验证与可复用证据

实际调用本期依赖且具备合法输入的安全查询，核验真实字段及必要的只读组合路径；在可安全达到的条件下补空结果和参数边界，不为覆盖而制造订单、压力或账号变更。记录时间、定义版本、脱敏输入输出、关键结论、证据路径与哈希。凭据和真实个人资料不进入 PRD、用例或共享样本。

能力和组合路径分别标注定义已读、本轮查询验证、历史证据、模拟、真实业务验证、失败或 blocked，并标出证据支持的具体范围。文档定义可支撑条件性设计，但不证明业务已跑通。缺输入、认证或环境时记录原因、影响、验证方法和责任方；安全查询通过不能替代交易、PA、设备及性能验证。下单、支付、取消等动作仅在明确授权范围内执行；模拟、dry-run 和历史样本单独标注。

## 两个独立公共需求

项目明确暂缓认证与个人信息工作时，本节不展开、不新增设计或测试，保留原件与范围决定，待用户恢复。

### 首次使用的认证与授权

核实认证状态查询、手机认证入口、PA 引导手机的能力、当前用户与服务账号绑定、授权结果回传／查询、有效期、失效和取消／失败恢复。认证由手机承接，FA 本体仍纯语音；手机号资料不直接作为认证成功凭据。服务端确认成功后续接原任务，明确保存进度、跨端关联与恢复依赖。认证流程须绑定发起用户，防止串号。仅当业务确需账号时触发；不需认证的服务说明适用范围。

### 个人信息获取、复用与保存

姓名、地址、手机号等按当前任务必要字段获取，顺序为 PA → 用户给定 MCP／CLI／API → 询问用户。前一渠道只缺部分字段时仅补缺失字段；渠道不可用与字段缺失分别记录，不用猜测代替查询。核实资料所属用户、字段含义、时效及使用权限；多地址、冲突或影响履约的信息进行必要确认，用户本次明确修改优先。信息变更使相关报价／结果失效时重新计算。

区分当次使用与长期保存。核实 PA 读取、写回、更新和保存授权契约；新信息当次使用，长期保存优先写回 PA，依实际能力和授权执行。不能默认 PA 有写接口或 FA 有资料库；外部服务回写也须明确能力和授权。缺少长期保存能力时如实限制，不影响有依据的当次使用。两项需求分别映射功能、交互、流程图分支和测试 case；必要能力缺失移入缺口，不能承诺完成。复验不同用户隔离、授权过期、手机认证中断、信息缺失／冲突／修改及写回不可用路径。

## 五类交付及四阶段验收

沿用主 skill 的 artifacts 和稳定 ID，五类材料可作为同一交付包的不同分区，不强制另建文件或 schema：

| 交付 | 最低内容 |
|---|---|
| 全量能力台账 | 文档与示例覆盖清单、提供范围、逐项能力覆盖、业务含义、输入输出、限制、副作用及状态 |
| 业务组合路径 | 参数传递、上下文、失效、终点凭据和恢复 |
| 可实现性矩阵与机会 | 功能／动作关联能力及 PA 依赖、输入来源、可用输出、结论和缺口；附组合机会 |
| 验证证据包 | 可复用脱敏样本、查询及组合证据、范围、时间和哈希 |
| PA 依赖与能力缺口 | 未核实项、功能影响、缩小承诺方案及补证方式 |

四次能力验收沿用主合同的 standards、receipts 和消费者验收记录，并按 [能力强制验收](../../atomic-to-fa-prd/references/capability-gates.md)维护 schema 4 的 `capability_validation` 文件。每次引用本节点当前版本输入文件及实际哈希，逐项写观察、证据和结论；下游标准先于交付定义。requirements／interaction／cases／final 必验内容为：

| 节点 | 必验内容 |
|---|---|
| 需求形成 | 文档／示例覆盖及缺项影响已明确；本期逐业务动作能力映射、必要输入来源、关键组合连续性和完成依据成立 |
| 交互完成 | 提问与候选、确认与修改后失效、失败／未知结果恢复、结果播报均由真实能力及 PA 基线支撑 |
| 测试集形成 | 预期动作与返回可核验；禁止动作遵守授权；关键规则、组合及失败分支有正负用例，执行方式和未验证状态准确 |
| PRD 收敛 | 正文、附录、交互、两图和用例对能力、前提、授权、结果与恢复的承诺一致；变更已更新证据和受影响项 |

每次能力专家实际读取同版产物后复验，产品／交互／测试等消费者仍独立验收其接收件。受阻可记录验证缺口；缺必要能力的产品承诺必须返回修订，不能用结构通过或带限制通过消除问题。

验收要求：给定能力逐项有结论或明确覆盖缺口；本期每个外部业务动作有具体工具／命令／端点及可获取的必要输入；FA 派生加工由 discovery v2 的真实输入字段、可复核规则与结果边界支撑，PA 步骤由已确认依赖支撑；关键组合能衔接；结果判断有返回依据；必要安全查询有证据或明确阻塞；未验证状态可见；无必要能力支撑的承诺已缩小或移出本期。测试发现返回不符或设计新增承诺时，更新能力证据、受影响功能／节点／图分支／case 并重新验收，不另建测试预期。

五类材料放 PRD 附录；正文只写影响用户任务的功能、限制和关键决定。六章模板、两张原生可编辑流程图、独立飞书测试表链接及固定指标保持不变。
